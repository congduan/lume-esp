04 / FAQ

The useful caveats.

Read this before treating a code-complete feature as board-proven.

What are the resource limits?

The target board has 8 MB PSRAM and 16 MB flash per README. The type file caps a Canvas at 480×480 and a shared 460,800-byte RGB565 canvas budget. A single Fs.readBinary call is limited to 64 KiB. These are contract limits, not measured end-to-end app memory usage.

What has been tested on a real board?

The roadmap marks code and host-harness work separately from device acceptance. USB push latency, WiFi association and HTTP, audio playback and recording, sleep current and touch wake reliability, IMU readings, and display visuals still need on-device acceptance.

Is WiFi OTA or a host simulator available?

Yes. The host simulator is available, and the CLI implements HMAC-authenticated WiFi OTA. OTA radio behavior still needs board acceptance; the virtual network runner has not yet passed WiFi association.

Why is the time wrong after reboot?

Wall-clock time needs WiFi with an IP address and a successful SNTP sync via lume.system.setTimeNtp(). The clock, clock_round, watchface, and weather apps attempt SNTP; their fallback behavior differs. After reboot an app must sync again, and an offline device may show uptime or an unsynced state.

Can I test WiFi without a board?

Run tools/emu-net/run.sh examples/net_check after installing esp-emu and the dependencies in tools/emu-net/README.md. It checks [NETCHECK] serial steps over virtual WiFi and writes artifacts/emu-net/net_check/serial.log. The recorded r144 run still fails association before IP and HTTP checks; this is a test path, not a passed board-radio result.
